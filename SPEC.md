# TaskBridge Notification & Audit Service — Technical Specification

**Status:** Assessment specification; implementation is out of scope.
**Scope:** A standalone, multi-tenant service for recording immutable audit events and delivering in-app notifications about Project Service changes. It owns its data store and communicates with other services only through APIs or messaging contracts.

## 1. Data model

PostgreSQL types are shown. UUIDs are generated by the service; timestamps are UTC. Every record is tenant-scoped.

### AuditLog

| Field | Type | Constraints / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `tenant_id` | `uuid` | Required; derived from trusted identity/event |
| `event_id` | `uuid` | Required; unique per tenant for idempotent ingestion |
| `actor_id` | `uuid` | Nullable for system-originated events |
| `event_type` | `varchar(100)` | Required; allow-listed event name |
| `resource_type` | `varchar(100)` | Required; e.g. `Project` |
| `resource_id` | `uuid` | Required; identifier owned by the originating service |
| `occurred_at` | `timestamptz` | Required; source event time |
| `recorded_at` | `timestamptz` | Required; service-assigned ingestion time |
| `details` | `jsonb` | Optional, bounded change metadata; exclude secrets and unnecessary student data |
| `source_ip` | `inet` | Optional; captured only when supplied by a trusted source |
| `user_agent` | `varchar(512)` | Optional; captured only when supplied by a trusted source |

Indexes: unique `(tenant_id, event_id)` and `(tenant_id, resource_type, resource_id, recorded_at)`.

### Notification

| Field | Type | Constraints / purpose |
|---|---|---|
| `id` | `uuid` | Primary key |
| `tenant_id` | `uuid` | Required; tenant scope |
| `event_id` | `uuid` | Required; originating event, unique with tenant and recipient |
| `recipient_id` | `uuid` | Required; recipient identity |
| `type` | `varchar(100)` | Required; allow-listed notification type |
| `title` | `varchar(200)` | Required |
| `body` | `varchar(2000)` | Required; must not include unnecessary sensitive data |
| `resource_type` | `varchar(100)` | Optional; related resource kind |
| `resource_id` | `uuid` | Optional; related resource identifier |
| `created_at` | `timestamptz` | Required; service-assigned UTC time |
| `read_at` | `timestamptz` | Nullable; set once when recipient marks it read |

Indexes: unique `(tenant_id, event_id, recipient_id)` and `(tenant_id, recipient_id, created_at)`.

## 2. API contracts

All endpoints use `/api/v1`, HTTPS, JSON, and a validated JWT. Tenant identity comes from trusted claims, never from request data. Errors use `{"error":{"code":"...","message":"..."}}`; do not expose stack traces.

### Query audit history

`GET /api/v1/audit-logs?resourceType=Project&resourceId={uuid}&from={UTC timestamp}&to={UTC timestamp}&limit=50&cursor={opaque}`

`200 OK`: `{"items":[{"id":"uuid","eventId":"uuid","actorId":"uuid","eventType":"PROJECT_STATUS_CHANGED","resourceType":"Project","resourceId":"uuid","occurredAt":"UTC timestamp","recordedAt":"UTC timestamp","details":{}}],"nextCursor":"opaque-or-null"}`

### List notifications

`GET /api/v1/notifications?unreadOnly=true&limit=50&cursor={opaque}`

`200 OK`: `{"items":[{"id":"uuid","type":"PROJECT_STATUS_CHANGED","title":"Project updated","body":"A project changed status.","resourceType":"Project","resourceId":"uuid","createdAt":"UTC timestamp","readAt":null}],"nextCursor":"opaque-or-null"}`

### Mark notification read

`PATCH /api/v1/notifications/{id}/read` — no request body.

`200 OK`: `{"id":"uuid","readAt":"UTC timestamp"}`. Repeated requests are idempotent and return the existing read time. Unknown or inaccessible IDs return `404`.

Project event ingestion is asynchronous (see §3); it is not a public client write endpoint. Successful event acceptance is acknowledged by the messaging adapter; duplicate events are safely ignored.

## 3. Project Service integration

The Project Service remains the source of truth for project state. After a committed project state change, it publishes a versioned event through the agreed messaging abstraction. Minimum event envelope: `eventId: uuid`, `tenantId: uuid`, `projectId: uuid`, `eventType: string`, `occurredAt: UTC timestamp`, `actorId: uuid|null`, and relevant old/new state. The Notification & Audit Service consumes the event, appends an audit record, and creates recipient notifications. It does not read or write the Project Service database.

Delivery is at least once: `(tenant_id, event_id)` and `(tenant_id, event_id, recipient_id)` uniqueness makes processing idempotent. Persist the audit record and generated notifications atomically. Recipient resolution must use an authorized membership/identity contract scoped to the event tenant; exact audience rules and event schema are assumptions to confirm with the service owners.

## 4. Security, immutability, and validation

- Require authenticated service identity for event ingestion and claims-based user authorization for reads and read-state updates. Enforce least-privilege roles/scopes; users may read only their own notifications, while audit access requires an explicitly authorized auditor/educator role.
- Derive tenant scope from trusted JWT claims or authenticated event envelope, validate service-to-service provenance, and apply tenant filtering to every lookup and write. Never trust client-supplied tenant IDs. Cross-tenant IDs must not disclose record existence.
- Audit logs are append-only: no update or delete API, application mutation path, or ordinary database role permission may modify or remove them. Enforce database-level protections (restricted grants and an update/delete rejection trigger or equivalent), and audit administrative access. Corrections are new compensating events, not edits. Retention/deletion exceptions require an approved compliance policy; none is assumed here.
- Validate UUIDs, timestamps and ranges (`from <= to`); allow only registered event/resource types; require non-empty bounded title/body and identifiers; cap `limit` at 100; bound `details` size and allowed keys; reject malformed JSON and unsupported content types. Ignore/deny request tenant overrides. Require recipient and resource references to belong to the event tenant. Return `400` for invalid input, `401/403` for authentication/authorization failures, and `404` for missing or out-of-scope records.
- Do not place credentials, tokens, or unnecessary student PII in audit details or notifications. Use parameterized database operations and TLS for service/API traffic.

## 5. Copilot assistance and human review

GitHub Copilot Chat helped draft and refine the service-focused structure, field lists, API examples, integration flow, and validation checklist from the requested requirements. Constraint-based prompting kept the scope documentation-only; iterative refinement shifted the prior Project Service-centered material to the Notification & Audit Service. Human judgment corrected the service boundary to avoid shared database access, aligned proposed types and platform assumptions with repository guidance (.NET/PostgreSQL), and marked event schema and recipient rules as assumptions rather than established facts. This specification is a design artifact, not evidence that the service or contracts already exist.
